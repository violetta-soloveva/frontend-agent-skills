# Resolve vulnerabilities

Goal: clear every **High and Critical** vulnerability (CVSS 7.0 or higher) with the fewest, smallest dependency changes. Fix Medium and Low ones only when the fix is easy. Every override or ignore that remains carries a documented reason.

## Severity scope

- **High / Critical (CVSS ≥ 7.0)**: must be resolved. Climb the whole fix ladder.
- **Medium / Low (CVSS < 7.0)**: fix only with the easy rungs, `npm audit fix` or an in-range minor/patch update. If those don't clear it, stop. Don't propose an override, major bump, or ignore. List it in the chat summary as left unresolved, with the reason (for example, "fix only in 11.x, parent accepts ^10").

## Ground rules

- Change dependencies only through npm commands and `package.json`. `package-lock.json` is regenerated by `npm install`, never hand-edited.
- Apply `npm audit fix` and minor/patch bumps yourself, without asking.
- **Always ask before** adding an override, applying a major bump (direct or via an override), or adding an ignore. In the question, name the package, the target version, the parent's accepted range, and the vulnerabilities it fixes. Apply it only if the user agrees.
- Ask the user whenever a choice is unclear: which rung to use, whether a bump is safe, whether an advisory really applies.
- Touch only `package.json`, `package-lock.json`, `osv-scanner.toml`, and `osv-override.md`. Leave other modified files in the working tree alone.

## Steps

### 1. Scan

```sh
pre-commit run osv-scanner --all-files
```

The scanner output is the source of truth, not `npm audit` or the user's summary: record every row (id, CVSS, package, installed version, fixed version). Done when you hold the full list, with each row marked High/Critical or Medium/Low.

### 2. Trace each package

For every package in the list:

```sh
npm ls <pkg>                 # who pulls it in; "overridden" means an override pins it
npm view <parent>@<ver> dependencies   # the range the parent accepts
npm view <pkg> versions      # whether a fixed version is published
```

Check `overrides` in `package.json` and the entries in `osv-scanner.toml`: an exact-version override blocks `npm audit fix` from moving the package. Done when each package has a parent, the parent's accepted range, and the nearest fixed version.

### 3. Climb the fix ladder

Take the first rung that works for each package, re-scanning after each change. Rungs 1–2 apply to every severity. Rungs 3–4 apply only to High/Critical, and only after the user agrees:

1. **`npm audit fix`** (never `--force`).
2. **Update the package or its parent directly**, when the fix is a minor or patch bump: `npm install <pkg>@^<fixed>` (`-D` for dev dependencies). A parent whose range already includes the fixed version needs only a reinstall.
3. **Override or major bump** *(ask first)*, when a fixed version exists but the parent's range excludes it. Either bump the parent to a major that accepts the fix, or add a scoped override in `package.json` (`"overrides": { "<parent>": { "<pkg>": "<fixed>" } }`) and document it (see [Documenting](#documenting)).
4. **Ignore** *(ask first)*, when no fixed version exists or the user declined rung 3: add an `IgnoredVulns` entry to `osv-scanner.toml` and document it there.

Done when the package's vulnerabilities leave the scan, sit on rung 3 or 4 with documentation, or (Medium/Low, or declined by the user) are noted as unresolved for the summary.

### 4. Prune stale workarounds

For every existing override and ignore entry, test whether it is still needed: remove it, run `npm install`, check `npm ls <pkg>`, re-scan. Keep it only if the vulnerability returns. Remove the matching row from `osv-override.md` with each dropped override, and the file itself once it is empty.

### 5. Verify

```sh
npm install
pre-commit run osv-scanner --all-files
npm run test:ci              # when dev tooling or runtime packages changed
```

Done when no High/Critical rows remain in the scan, tests pass, and `git status` shows only the files listed in Ground rules. The hook may still fail on Medium/Low rows left unresolved; say so in the summary.

### 6. Summarize in chat

Write the summary as your final chat message. Don't create a report file. Start with a numbered list of the steps you actually took, in order, each with the command run and what it showed or changed. For example:

1. Scanned with `pre-commit run osv-scanner --all-files`: found follow-redirects 1.16.1 (CVSS 8.2) and minimatch 10.2.5 (CVSS 6.9, dev).
2. Traced with `npm ls`: follow-redirects comes from `axios@1.20.0` (`^1.16.0`, fix fits); minimatch comes from `typescript-eslint` (`^10.2.2`, fix only in 11.x).
3. Ran `npm audit fix`: follow-redirects 1.16.1 → 1.16.3.
4. Checked the existing braces ignore: still needed, no patched release.
5. Re-scanned: only minimatch remains.
6. Ran `npm run test:ci`: all tests passed.

Then list what changed per vulnerability (rung used, old → new version) and any overrides or ignores added or removed. Then list what is still unresolved: Medium/Low rows with no easy fix, and anything the user declined, each with its fixed version and why it wasn't applied. If any of these remain, note that the hook still fails.

## Documenting

**Override**: add a row to `osv-override.md` at the repo root (create it if missing):

```md
# OSV dependency overrides

Temporary npm `overrides` documented here until upstream packages ship fixed versions.

| Package override | Version | Parent dependency | OSV |
| --- | --- | --- | --- |
| `undici` | `6.27.0` | `@sentry/cli@3.5.1` (was `6.24.1`) | [GHSA-vxpw-j846-p89q](https://osv.dev/GHSA-vxpw-j846-p89q) (CVSS 7.5) |
```

**Ignore**: add an entry to `osv-scanner.toml` with a revisit date about three months out and links to the discussion:

```toml
# TODO: Check for a fixed version in three months (DD.MM.YYYY).
# slack = "<thread link>"
# github_pr = "<PR link>"
[[IgnoredVulns]]
id = "GHSA-xxxx-xxxx-xxxx"
ignoreUntil = YYYY-MM-DD
reason = "<why it cannot be fixed and why the risk is acceptable, e.g. dev-only, trusted input>"
```

Ask the user for the Slack and PR links when they are not known.
